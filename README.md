# 门店带看与转化管理系统

房产中介门店内部工具：房源档案、带看登记、客户跟进状态机、门店漏斗、滞销提醒、经纪人月报、CSV 导出。

## 运行

```bash
pip install -r requirements.txt
streamlit run app.py
```

首次启动自动写入样例数据（8 个经纪人、10 套房源、14 个客户、20 条带看、2 笔成交），
日期相对当天生成，当月漏斗和各类提醒开箱可见。删除 `store.db` 后重启即可重置。

> 升级提示：业务约束（CHECK/触发器）建在数据库层，旧版 `store.db` 启动时会被识别并拒绝，
> 删除 `store.db` 重启即可（样例数据会自动重建）。

## 测试

```bash
python -m unittest discover -s tests -v
```

## 结构

| 文件 | 职责 |
|---|---|
| `app.py` | Streamlit 页面（只展示和收集输入，无 SQL；页面校验仅为 UX） |
| `services.py` | 业务逻辑与**强制校验**：存在性/状态/值域校验、状态推进、漏斗统计、提醒、月报 |
| `repository.py` | 全部 SQL（数据读写） |
| `state_machine.py` | 客户状态流转校验（独立模块，不碰数据库） |
| `db.py` | SQLite 连接与建表；**最后防线**：CHECK 约束、唯一索引、触发器 |
| `options.py` | 页面下拉选项构造（键强制带主键 id，防同名字段互相覆盖记错对象） |
| `seed.py` | 样例数据 |
| `tests/` | unittest：状态机、服务层拦截、数据库层拦截、漏斗统计、提醒逻辑 |

## 分层防御

同一条业务规则在三层各落一次，任何一层被绕过都不会产生脏数据：

1. **页面层**：隐藏不可用选项、即时报错（仅为体验，不是防线）
2. **服务层**：每个写函数入口校验——终态客户不能登记带看、成交房源必须在售、
   一房/一客至多一笔成交、价格必须为正的有限数字（拒 NaN/Inf/布尔）、文本非空且有长度上限、
   户型合法、引用必须存在且经纪人在职、反馈不可重复、日期必须真实存在（拒 2026-02-31）、
   业务时间不能是未来且时间线自洽（带看不早于建档/挂牌、成交不早于挂牌/首次带看、
   进入「带看」状态必须先有带看记录）
3. **数据库层**：`status`/户型枚举、价格有限正值与文本长度 CHECK（注册了真实日历
   SQL 函数，2026-02-31、99:99:99 无法入库）、`deals(customer_id)`/`deals(property_id)`
   唯一索引，以及触发器——状态变更必须先有匹配的合法历史（防跳过留痕）、
   进入「带看」必须存在带看记录、终态客户禁插带看、带看/成交的时间线一致性、
   成交单要求客户已成交且房源在售、已成交房源不可回退

## 业务规则

- 客户状态只能按 **新客 → 带看 → 谈价 → 成交** 逐级推进；任意进行中状态可转 **流失**；成交、流失为终态
- 成交必须登记成交房源、成交价与**成交经纪人**（`close_deal`，业绩归实际成交人，默认负责经纪人可改），房源随即标记「已成交」
- 新客首次登记带看后，状态自动推进为「带看」
- 带看后 **24 小时内**必须补客户反馈，超时在门店大盘提醒
- **挂牌超 45 天且近 14 天无带看** 的在售房源 → 滞销提醒（该催房东调价了）
- 所有登记记录操作人（侧边栏填写）与本地时间；状态变更全程留痕

## 并发模型（多人同时使用）

- **每会话独立连接**：页面用 `st.session_state` 为每个浏览器会话建立独立 SQLite 连接，
  绝不跨用户共享——否则 A 的多步事务会被 B 的 `commit` 连带提交、被 B 的 `rollback` 连带回滚
- **写事务串行化**：所有写操作用 `BEGIN IMMEDIATE`，进入即持有唯一写锁，事务内"读状态→校验→写入"
  不再有竞态窗口；后来者排队，等待超过 5 秒（`busy_timeout`）得到友好的"系统繁忙，请稍后重试"
- **WAL 模式**：文件库开启 WAL + `synchronous=NORMAL`，多人同时用时读不阻塞写、写不阻塞读，
  读事务也读不到别人未提交的半截数据（`:memory:` 库自动跳过）
- **约束兜底**：即使两个请求几乎同时提交，唯一索引与触发器仍保证一房只成交一次，输家收到业务错误
- **并发首启**：多个会话同时首次打开时，样例数据只灌一次（唯一约束 + 冲突后重查安静跳过）

## 统计口径（漏斗 / 月报 / 成交列表必须对得上）

- **时间口径**：一律按业务实际发生时间——新客按登记时间、带看按带看时间、**成交按成交日期 `deal_date`**
  （不是系统录入时间，跨月补录也算在成交当月）。因此同月「漏斗成交数 = 月报成交合计 = 大盘成交列表条数」
- **归属口径**：带看归实际带看经纪人，成交归实际成交经纪人，均按操作时选择的经纪人计入
- **人员范围**：历史月报包含已离职经纪人及其历史业绩（新操作的选择器仍只列在职），合计不因离职而蒸发
